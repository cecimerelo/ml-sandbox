# Example datasets

One file per path through the upload control, so every refusal can be seen rather than
taken on trust. Generated by `uv run python scripts/make_examples.py`.

| File | What it shows |
|---|---|
| `houses.csv` | Accepted — 400 rows, mixed types, some gaps |
| `houses-with-notes.csv` | Accepted, with a date and a free-text column **skipped and named** |
| `too-many-columns.csv` | Refused — 512 columns against a limit of 500 |
| `header-only.csv` | Refused — a header row and no data |
| `one-column.csv` | Refused — nothing to predict *from* |
| `all-unsupported.csv` | Refused — every column is free text |
| `not-a-csv.png` | Refused — not a CSV at all |
| `too-large.csv` | Refused **in the browser**, before any upload begins |

## Two of these are worth trying deliberately

**`houses-with-notes.csv`** is the interesting acceptance. A date column and a column of
agent's notes are excluded and reported, and the file is still usable. Refusing the whole
thing over one date column would make you do the work the tool exists to save you.

**`too-large.csv`** never reaches the server. Watch the network tab: there is no request.
That is the point of checking size in the browser, and it is the only rule that lives in
two languages — `tests/test_upload.py` asserts the two numbers agree.

## Why `too-large.csv` is not committed

It is fifty-six megabytes of noise. `scripts/make_examples.py` writes it and `.gitignore`
keeps it out; everything else here is small enough to keep.

## They are checked

`tests/test_upload.py` runs each of these through the reader and asserts it produces what
this table claims. Examples that drift from the rules quietly stop being examples.

## `strong-signal-houses.csv` — not an upload path, a training demo

Every file above is generated by `scripts/make_examples.py` to exercise one path through
`mlsandbox.upload.read`. This one is not — it exists for #4 (training the recommended
method live), where `houses.csv`'s `price` is deliberately pure noise (`rng.normal(...)`,
independent of every other column, since the point there was the upload path, not
predictive value). Trying to demonstrate that training actually finds something on a file
built to have nothing to find is a demo working against its own fixture.

`strong-signal-houses.csv` prices each row from its own columns plus modest noise
(`1200 × size_m2 + 8000 × bedrooms + a city/garden premium + noise`), so a trained method's
score reads as real evidence of something — verified directly with `cross_val_score`
before committing it: linear regression, random forest and KNN all land between 0.95 and
0.99 R², not the ~0 every method gets on `houses.csv`.

## `binary-sales.csv` — the same idea, for classification

Regression's training demo needed real signal; classification's needs the same thing, plus
an actual two-class target to exercise #96's ROC curve and confusion matrix. `sold` is
`"yes"`/`"no"`, thresholded at the median of `0.08 × size_m2 + 1.2 × bedrooms + noise` — a
real, if noisy, separation between the two classes, not a coin flip. Verified with
`cross_val_score` before committing it: logistic regression lands at 0.81 balanced accuracy
across 5 folds, not the ~0.5 chance level a label with no relationship to the columns would
give.

## `linear-regression-demo.csv` — for #95's chart panel specifically

`strong-signal-houses.csv` works for this too, but only has two numeric predictors — the
coefficient plot is sparse, and every point sits close enough to the pack that the leverage
plot has nothing to point at. This file has five (`size_m2`, `bedrooms`, `age_years`,
`distance_km`, `garden_m2`, each with a distinct sign and magnitude in `price`'s true
coefficients) plus two deliberately planted high-leverage rows — a much larger property and
a much smaller, farther one — so the leverage chart has real "worth a second look" points to
show, not just noise. Verified with `cross_val_score` before committing it: linear
regression lands at R² ≈ 0.97 across 5 folds.
